# Controle de Manutenções

Sistema web (PWA) para registrar e comprovar manutenções de ar-condicionado, caixas d'água, portas corta-fogo e luzes de emergência, feitas por um técnico para empresas clientes. Duas áreas: `/tecnico` (admin, com partes offline) e `/portal` (empresa, somente leitura e online).

**Fonte da verdade do produto: [`docs/ESCOPO.md`](docs/ESCOPO.md)** (funcionalidades, modelo de dados, arquitetura, stack, UX). Leia antes de qualquer decisão. O projeto é construído em 5 etapas; não implemente funcionalidades de etapas futuras.

> O Next.js desta versão (16.x) tem mudanças importantes (ex.: `proxy.ts` no lugar de `middleware.ts`). A documentação certa está em `node_modules/next/dist/docs/` — consulte-a em vez de confiar na memória (ver também `AGENTS.md`).

## Comandos

Gerenciador de pacotes: **pnpm** (Node 22+; na Hostinger use Node 22 LTS).

| Comando | O que faz |
| --- | --- |
| `pnpm dev` | Servidor de desenvolvimento (http://localhost:3000) |
| `pnpm build` / `pnpm start` | Build e servidor de produção (processo Node comum). O `build` roda `next build --webpack`: na Hostinger o Turbopack falhou ao processar o CSS (processo filho do Turbopack saiu sem conectar); o `pnpm dev` continua em Turbopack |
| `pnpm lint` / `pnpm typecheck` | ESLint / `tsc --noEmit` |
| `pnpm test` | Testes unitários (Vitest): status, checklist, storage |
| `pnpm db:generate` | Gera migration a partir de `db/schema.ts` (drizzle-kit) |
| `pnpm db:migrate` | Aplica as migrations no Neon |
| `pnpm db:seed` | Tipos de equipamento + usuário admin (`SEED_ADMIN_*`). Idempotente |
| `pnpm db:seed:demo` | 1 cliente, 3 locais, 12 equipamentos e serviços variados (sem fotos). Idempotente |
| `pnpm db:usuario --nome … --email … --senha … --papel admin\|cliente` | Cria um acesso pela linha de comando (o dia a dia é pela tela `/tecnico/acessos`) |

Os scripts `db:*` leem o `.env` (`node --env-file=.env`). Variáveis: veja `.env.example`; são validadas por Zod em `lib/env.ts`.

## Convenções

- **UI 100% em português do Brasil**, simples, sem jargão ("Salvar serviço", "Sem internet — seu registro está salvo no celular"). Erros dizem o que fazer ("Preencha a data do serviço").
- **Só componentes shadcn/ui** (`components/ui`, estilo `radix-nova`, todos instalados). Não adicionar outra biblioteca de UI nem bibliotecas fora da stack do escopo sem perguntar. Ícones: lucide-react.
- **UX (escopo, seção 9) — obrigatória**, o usuário principal tem mais de 40 anos:
  - fonte base 17 px no celular / 16 px no computador (escala em `rem`; `text-xs` = 14 px, nada menor);
  - botões, inputs e selects com **mínimo de 48 px** no celular — já ajustado nas variantes dos componentes em `components/ui` (não ajuste tela por tela);
  - alto contraste, foco visível, tema claro apenas;
  - **ícones sempre com texto**; uma ação principal por tela; botão Voltar sempre visível;
  - rótulos sempre visíveis acima dos campos; valores padrão inteligentes; ação destrutiva sempre com `AlertDialog` explicando a consequência;
  - toda ação com retorno (toast Sonner), carregamento com Skeleton/Spinner, estados vazios com explicação + botão de próxima ação;
  - **status sempre com cor E texto**: use `components/status-badge.tsx` (tokens `em_dia`, `vence_em_breve`, `vencido`, `sem_registro` em `globals.css`);
  - datas dd/mm/aaaa e números com vírgula: use **sempre** `lib/format.ts`.
- **Regra de ouro do offline:** as telas do técnico que funcionam offline (lista/detalhe de equipamentos, registro de serviço, histórico, leitor de QR) são **Client Components** e acessam dados **somente** por `lib/tecnico/data` (leitura por hooks `useEquipamentos`, `useEquipamento`, `useServicos`, `useTipos`, `useTipo`, `useLocais`, `useClientes`, `usePainel`; escrita por `repositorio.*`). Nunca `fetch`, `db`, Server Component ou Server Action nessas telas. Desde a etapa 5 a implementação é Dexie + fila de envio (`lib/tecnico/data/dexie-repositorio.ts`, escolhida em `atual.ts`); a implementação antiga por API (`fetch-repositorio.ts`) segue sendo usada por baixo para cadastros e edição/exclusão de serviço. Telas de cadastro e o `/portal` podem usar Server Components.
- **Permissões (obrigatório):** sempre pelo helper `lib/auth/permissoes.ts` — `getSessaoOuRedirect()`, `exigirAdmin()`, `comAdminApi()` (route handlers) e `escopoCliente()`. **Nenhuma query do portal (ou de usuário `cliente`) pode ignorar `escopoCliente()`**: toda consulta filtra por `escopo.clienteId`. O `proxy.ts` é só checagem otimista de cookie; a proteção real é no servidor.
- **IDs são UUID** (gerados no cliente para registros que nascem offline). Datas de calendário (`data`, `proxima_data`) são `yyyy-mm-dd` (string), sem fuso.
- **Nomes de domínio em português, conforme o schema** (`clientes`, `locais`, `tipos_equipamento`, `equipamentos`, `servicos`, `fotos`, `usuarios`; campos `periodicidade_dias`, `proxima_data`…). Exceção: as colunas do Better Auth usam propriedades em inglês (`name`, `email`, `createdAt`…) com nome físico em português — ver comentário em `db/schema.ts`.
- JSONB tipado e validado com Zod em `lib/schemas/` (`campo.ts`, `checklist.ts`). O checklist de um serviço guarda **snapshot do rótulo**.
- Fotos: disco do servidor em `UPLOAD_DIR`, sempre via interface única `lib/storage/`; nunca públicas (só por `GET /api/fotos/[id]`).
- **Hospedagem: Hostinger Node.js Web Apps**, processo Node (não serverless). Nada específico da Vercel (Edge, `@vercel/*`, Blob, Cron). A Hostinger aplica `output: "standalone"` sozinha: por isso o `next.config.ts` **não** define `output` e deve continuar exportando um **objeto** (não função). O CSS (Tailwind 4) passa por `postcss.config.mjs` (`@tailwindcss/postcss`). Pacotes usados no build e na inicialização (`tailwindcss`, `typescript`, `@types/*`, `serwist`, `@serwist/turbopack`, `esbuild`) ficam em `dependencies`, para funcionar mesmo se o servidor não instalar as `devDependencies`. Build `build`, diretório de saída `.next`, Node 22.

## Estado atual

**Etapa 1 (fundação) — concluída.** Projeto Next.js 16, shadcn/ui (Radix, todos os componentes), design system acessível, Drizzle + Neon (schema da seção 5, migration inicial, seeds), Better Auth sem cadastro público, helper de permissões, layouts de `/tecnico` e `/portal`, camada `lib/tecnico/data`.

**Etapa 2 (cadastros, busca e QR Code) — concluída.**

- **Clientes e locais** (`/tecnico/clientes`): Cards, criar/editar em Dialog (computador) ou Drawer (celular) via `components/dialogo-responsivo.tsx`; CNPJ com máscara e validação; excluir local só sem equipamentos (AlertDialog explica). Com 1 cliente só, nenhuma tela mostra seletor de cliente: use `useClienteAutomatico()` (`precisaEscolher` só é verdadeiro com 2+ clientes).
- **Tipos** (`/tecnico/tipos`, `/tecnico/tipos/novo`, `/tecnico/tipos/[id]`): lista e editor em página própria (dados, campos, checklist; subir/descer por botão; `key` gerada ao salvar e imutável depois; pré-visualização ao vivo; aviso ao remover campo com valores; arquivar/reativar; excluir só sem equipamentos).
- **Equipamentos** (`/tecnico/equipamentos`, `/novo`, `/[id]`, `/[id]/editar`): lista com busca instantânea (sem acento) e chips por situação/tipo/local/arquivados, ordenada por urgência (vencido → vence em breve → sem registro → em dia); formulário com campos dinâmicos (Zod gerado de `lib/schemas/atributos.ts`; em etapas no celular); detalhe com "Registrar serviço" (rota `/tecnico/servicos/novo?equipamento=id` ainda é placeholder), menu Editar / Ver QR Code / Arquivar e área reservada para a linha do tempo (etapa 3). Valores de campos removidos do tipo continuam guardados.
- **QR Code:** `https://<domínio>/e/{id}` gerado na hora com `qrcode` (`components/qr-code.tsx`). `/e/[id]` leva admin ao `/tecnico/equipamentos/[id]`, cliente a `/portal/equipamentos/[id]` (página mínima, escopada por `escopoCliente()`), e quem não está logado ao login com `?voltar=` (só destinos internos, `lib/auth/destino.ts`; o `proxy.ts` também usa `voltar`). `/tecnico/etiquetas`: escolha por equipamento/local/tipo e folha A4 (3 colunas) com CSS de impressão.
- **Camada de dados:** `lib/tecnico/data` agora tem escrita (`repositorio.salvarCliente/Local/Tipo/Equipamento`, `excluirLocal/Tipo`, `definirTipoAtivo`, `arquivarEquipamento`) além dos hooks; toda escrita dispara `notificarMudanca()` e os hooks recarregam. `useEquipamentos` carrega a lista uma vez e filtra em memória. Route handlers em `/api/tecnico/*` com `comAdminApi` e validação Zod (`lib/api.ts`, `lib/schemas/entidades.ts`, `lib/tecnico/mutacoes.ts`). Cadastros exigem internet.

**Etapa 3 (serviços, fotos, histórico e painel) — concluída.**

- **Fotos no disco:** `lib/storage` (interface `Armazenamento`: `salvar`, `ler`, `lerStream`, `existe`, `remover`; implementação em `disco.ts` sobre `UPLOAD_DIR`; chaves só por `chaveFoto`/`chaveMiniatura` com UUID validado, caminho conferido contra path traversal). `POST /api/fotos` (admin, multipart, JPEG/PNG/WebP até 2 MB, o `sharp` revalida, corrige rotação, limita a 1600 px e grava JPEG em `servicos/{servicoId}/{fotoId}.jpg`; idempotente). `GET /api/fotos/[id]` checa permissão (admin tudo; cliente só do próprio cliente via `escopoCliente()`; senão 404), faz stream com `Cache-Control: private` e aceita `?tamanho=miniatura` (~400 px, guardada em `miniaturas/`). Compressão no navegador em `lib/fotos/comprimir.ts` (browser-image-compression, ~250 KB). **Ordem do envio: fotos primeiro, serviço depois.** Como `fotos.servico_id` tem FK, a linha da foto é criada pelo `POST /api/fotos` só se o serviço já existe; senão é criada por `criarServico` (`lib/tecnico/servicos.ts`) a partir da lista de fotos do serviço, conferindo o arquivo no disco.
- **Serviços:** `POST /api/tecnico/servicos` idempotente (`insert … on conflict (id) do nothing`), `PUT/DELETE /api/tecnico/servicos/[id]` (excluir apaga os arquivos), `GET …/recentes`. Schemas em `lib/schemas/entidades.ts` (`servicoInputSchema`; descrição obrigatória). Camada de dados: `repositorio.salvarServico(dados, fotos, aoProgredir)`, `editarServico`, `excluirServico`, hook `useServicosRecentes`.
- **Registrar serviço** (`/tecnico/equipamentos/[id]/novo-servico`; editar em `…/servicos/[servicoId]/editar`): `components/servico/formulario-servico.tsx`, em etapas (tipo+data → checklist, pulada se o tipo não tem → fotos → descrição+próxima data → revisão), botões Voltar/Continuar fixos embaixo no celular (a barra inferior some nessas rotas), UUIDs do serviço e das fotos gerados ao abrir, snapshot do rótulo do checklist, progresso de envio, proteção contra duplo toque e confirmação ao sair com dados (AlertDialog; intercepta links internos e `beforeunload`). `/tecnico/servicos/novo` é a escolha do equipamento (Command com "Usados recentemente" e atalho para `/tecnico/escanear`).
- **Linha do tempo** no detalhe do equipamento (`components/servico/linha-do-tempo.tsx`): data, tipo, quem registrou, resumo do checklist (`lib/servicos/checklist.ts`), miniaturas com visualizador em tela cheia, Accordion de detalhes; editar/excluir só no computador (menu "Opções").
- **Painel** (`/tecnico`): saudação, "Registrar serviço", cartões Vencidos / Vencem em até 15 dias / Sem registro (abrem `/tecnico/equipamentos?situacao=…&tipo=…&local=…`), chips por tipo e local, 10 próximas manutenções e 5 últimos serviços.
- **Status:** regra única em `lib/status.ts` (`calcularStatus`, `ultimoServico`, `calcularStatusPorServicos`, `textoVencimento`, `textoStatus`), com testes. Use sempre essas funções (portal e PDF inclusive).

**Etapa 5 (PWA, offline e sincronização) — concluída.**

- **PWA:** Serwist (`@serwist/turbopack`, funciona tanto no build com webpack quanto no Turbopack). `app/sw.ts` é o service worker, servido por `app/serwist/[path]/route.ts` em `/serwist/sw.js` (escopo `/`); o precache leva todo `.next/static` (inclui fontes) + `public/` + `/offline`. Manifest em `app/manifest.ts` (`start_url: /tecnico`), ícones PNG gerados por `scripts/gerar-icones.mjs` em `public/icons/`. Só registra em produção, dentro do layout do `/tecnico` (`components/tecnico/registrar-sw.tsx`); SW novo fica "esperando" e aparece "Nova versão disponível — Atualizar" (`skipWaiting` só quando a pessoa toca). **Teste offline sempre com `pnpm build` + `next start`** (em `next dev` o SW não existe); o painel do navegador do Claude **não** suporta service worker — use Chrome/Edge de verdade.
- **Telas offline:** `/tecnico`, lista e detalhe de equipamentos, `…/novo-servico`, `/tecnico/servicos/novo`, `/tecnico/escanear`, `/tecnico/instalar`. O SW só guarda o HTML dessas rotas (lista em `app/sw.ts` e `lib/tecnico/offline.ts` — mantenha as duas iguais). Como o HTML de `/tecnico/equipamentos/{id}` embute o id, o app **aquece o cache** depois de cada sincronização (`lib/tecnico/sync/aquecimento.ts`: GET com `X-Aquecer`, 3 por vez, só o que falta). Qualquer outra tela offline cai em `/offline` ("Esta tela precisa de internet."); telas só-online usam `<Tela exigeInternet>`. `/e/{id}` sem internet vira redirect para o equipamento. Navegação suave que falha cai sozinha em navegação completa (por isso **não** usar `experimental.useOffline`).
- **Dexie** (`lib/tecnico/data/banco.ts`): `meta`, `clientes` (com locais), `tipos`, `equipamentos` (detalhe completo), `servicos` (10 mais recentes por equipamento), `filaServicos`, `filaFotos` (Blob comprimido). Os hooks usam `useLiveQuery`. O status dos equipamentos e a linha do tempo já contam a fila (`lib/tecnico/data/pendentes.ts`; selo "Aguardando envio", foto local por `FotoResumo.url`). Edição/exclusão de serviço, cadastros, acessos, relatórios e portal exigem internet. `salvarServico` só grava na fila e dispara a sincronização.
- **Sincronização:** servidor em `/api/sync/pull?desde=` (incremental por `equipamentos.atualizado_em` ou `servicos.atualizado_em`; excluir serviço também atualiza o equipamento) e `POST /api/sync/push` (lote ≤ 20, `criarServico` idempotente). Motor em `lib/tecnico/sync/`: push = fotos (`POST /api/fotos`) → lote de serviços → só então apaga da fila (nada sai sem confirmação); foto que falha não trava os outros; espera crescente 15 s … 15 min (`espera.ts`); 401/403 pausa e mantém a fila; 4xx permanente marca "recusado" (visível, "Tentar de novo"). Pull ao abrir, no `online`, ao voltar a aba e a cada 5 min; single-flight com Web Locks. Sem Background Sync (iPhone).
- **Interface:** `IndicadorSincronizacao` (4 estados + gaveta com pendências e "Sincronizar agora"), `ProvedorSincronizacao` e `SugestaoInstalar` no layout do técnico, `/tecnico/instalar` (Android com `beforeinstallprompt`, iPhone passo a passo), leitor de QR (`@yudiel/react-qr-scanner`; o wasm do ZXing é servido de `public/zxing/` para funcionar offline). Sair com pendências avisa e **nunca apaga a fila** (só os dados baixados e os caches).
- **Testes:** `lib/tecnico/sync/sync.test.ts` (fake-indexeddb + servidor simulado), `lib/qr.test.ts`. Fonte mínima do app: 16 px (`--text-xs`).

**Ainda não existe / limites conhecidos:** seletor de cliente no portal para o admin com 2+ clientes; a empresa não troca a própria senha; offline só os 10 serviços mais recentes por equipamento; equipamentos cadastrados depois só abrem offline após o próximo pull; fotos enviadas de um serviço que nunca chega a ser salvo ficam órfãs no disco (sem limpeza automática).
